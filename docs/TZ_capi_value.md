# ТЗ: доработка передачи Purchase в Meta Conversions API

**Проект:** Apollo Next — реклама Meta
**Дата:** 2026-07-29
**Кому:** разработчикам CRM / интеграции с Meta
**Оценка:** ~1 рабочий день разработки + 1–2 дня наблюдения

---

## 0. Коротко

Интеграция CRM → Meta CAPI **уже работает корректно**: события уходят server-side,
дублей с браузерным пикселем нет, матчинг настроен. Ничего перестраивать не нужно.

Задача — **изменить формулу поля `value`** и добавить несколько полей в существующий
payload. Это не новый пайплайн, а правка одного места.

---

## 1. Зачем

Сейчас в `value` уходит сумма первого платежа. Для месячных абонементов это
занижает реальную ценность клиента примерно в 3.5 раза (клиент в среднем платит
3–4 цикла), для годовых — не занижает (вся сумма уплачена сразу).

Из-за этого Meta видит годового клиента в 7–12 раз ценнее месячного,
хотя реально разница в 2–3 раза.

**Это не только вопрос отчётности.** В аккаунте есть 4 группы объявлений
с целью оптимизации `VALUE` — они делают ставки напрямую по этому числу.
Сейчас они систематически переоценивают охотников за годовыми абонементами
и недоинвестируют в месячные, которые дают основной объём.

---

## 2. Что меняем

### 2.1 Формула value

```
value = первый_платёж × k(тип_тарифа)
```

| Тип тарифа | Что входит | k | Комментарий |
|---|---|---|---|
| **monthly** | GymPass, SuperPass, SmartPass, TeenPass, MultiPass (4 недели) | **3.5** | стартовое значение, уточняется по когорте (раздел 5) |
| **annual** | любой годовой абонемент | **1.0** | вся сумма уплачена вперёд |
| **daily** | DailyPass | **1.0** | разовая покупка |

`первый_платёж` — фактически списанная сумма по сделке, в гривне.

**Коэффициент вынести в конфиг, не хардкодить.** Он будет пересчитываться
раз в квартал, менять его должно быть можно без релиза.

### 2.2 Промо «перша неділя за 1 ₴»

Если сделка стартует с промо-платежа 1 ₴, `первый_платёж` для формулы —
это **регулярная цена 4-недельного цикла по этому тарифу и клубу**, а не 1 ₴.
Иначе value будет 3.5 ₴ и Meta посчитает клиента бесполезным.

Событие `Purchase` при этом отправляется в момент, когда сделка фактически
оформлена (принята оферта / привязана карта), а не через неделю.

### 2.3 Членский взнос

Взнос (1 199 ₴, у 039 — 599 ₴, у 041 — 399 ₴) списывается на 42-й день.
В `value` его **не добавляем** — он за пределами окна атрибуции и
искажает сравнение с сегодняшними данными.
Учтём отдельно, в собственной аналитике.

## 3. Payload

Пример события. Полужирным — то, что добавляем или меняем.

```json
{
  "data": [
    {
      "event_name": "Purchase",
      "event_time": 1753790400,
      "event_id": "deal_884211",
      "action_source": "website",
      "event_source_url": "https://apollo.online/clubs/apollo-next-019-dream-town-1/",

      "user_data": {
        "em":  ["<sha256 email, lowercase, trimmed>"],
        "ph":  ["<sha256 phone, только цифры, с кодом страны, без +>"],
        "fn":  ["<sha256 имя, lowercase>"],
        "ln":  ["<sha256 фамилия, lowercase>"],
        "fbc": "fb.1.1753700000.PAQ0aXV...",
        "fbp": "fb.1.1753700000.1098765432",
        "client_ip_address": "...",
        "client_user_agent": "..."
      },

      "custom_data": {
        "currency": "UAH",
        "value": 4795.00,

        "order_id": "deal_884211",
        "content_ids": ["gympass_4w"],
        "content_type": "product",
        "content_name": "GymPass 4 тижні",

        "club_id": "019",
        "tariff_family": "monthly",
        "first_payment": 1370.00,
        "ltv_multiplier": 3.5
      }
    }
  ]
}
```

### 3.1 Обязательные поля

| Поле | Требование |
|---|---|
| `value` | по формуле из 2.1. Число, не строка |
| `currency` | **всегда одна и та же валюта.** Если сейчас шлётся UAH — оставить UAH. Не смешивать с USD ни при каких условиях |
| `event_time` | **время сделки**, не время отправки. Unix timestamp в секундах |
| `event_id` | уникальный ID сделки. Нужен для дедупликации |
| `order_id` | тот же ID сделки |
| `tariff_family` | `monthly` / `annual` / `daily` |
| `club_id` | код клуба (`019`, `034`, `041`…) |
| `first_payment` | фактически списанная сумма — для сверки, чтобы можно было пересчитать value задним числом, не трогая код |
| `ltv_multiplier` | применённый k — чтобы было видно в логах, какая версия формулы отработала |

### 3.2 `fbc` — отдельно и важно

`fbc` строится из параметра `fbclid`, который Meta добавляет в URL при переходе
по рекламе. Формат: `fb.1.<timestamp_ms>.<fbclid>`.

**Если сейчас `fbclid` не сохраняется в CRM вместе с UTM-метками — надо начать сохранять.**
UTM уже долетают корректно, значит механизм захвата параметров есть, добавляется
ещё одно поле. Без `fbc` матчинг держится только на email/телефоне — работает,
но заметно хуже, и часть сделок Meta не свяжет с рекламой вообще.

`fbp` — из cookie `_fbp`, ставится пикселем. Тоже сохранять, если ещё не сохраняется.

### 3.3 `action_source` — канал сделки

**Это, возможно, самая недооценённая часть ТЗ.**

В CRM попадают продажи трёх типов: с сайта, офлайн в клубе и через мобильное
приложение. В CAPI сейчас уходят все, и, судя по всему, все с одинаковым
`action_source: "website"`.

Если офлайн-продажа из клуба уходит как веб-событие, Meta сопоставляет её
с человеком по телефону/email и приписывает рекламе как view-through конверсию —
хотя человек просто пришёл в клуб. Это раздувает вклад рекламы и, что хуже,
учит алгоритм на сигнале, который к переходам с рекламы отношения не имеет.

**Косвенное подтверждение:** сейчас 62% конверсий, которые Meta себе приписывает —
view-through (увидел, не кликнул), 340 против 205 кликовых. Такая пропорция
как раз характерна для подмешанных офлайновых продаж.

**Что нужно:**

1. Определить канал сделки и проставлять корректно:

| Канал сделки | `action_source` |
|---|---|
| Покупка на сайте | `website` |
| Покупка в клубе (офлайн) | `physical_store` |
| Покупка через мобильное приложение | `app` |

2. Передавать канал ещё и явным полем в `custom_data` — для нашей аналитики:

```json
"custom_data": {
  "order_channel": "physical_store"
}
```

3. **Если поля канала в выгрузке сейчас нет** — это первое, что надо добавить.
   Без него правильно разметить события невозможно.

⚠️ Ничего не отключать и не переставать слать. Офлайн-продажи Meta принимает
и умеет с ними работать — но только если знает, что они офлайн.
Задача — разметить, а не отфильтровать.

### 3.4 Сроки отправки

Событие отправлять **сразу после оформления сделки**, в пределах часа.
Meta принимает события задним числом ограниченно, а для оптимизации
свежесть критична.

---

## 4. Чего НЕ менять

Перечисляю явно, потому что это частые «улучшения», которые ломают систему:

1. **Не фильтровать сделки по источнику.** Сейчас в CAPI уходят все сделки,
   а не только те, что CRM приписала Meta. Это правильно — Meta сама решает,
   какие связать с рекламой, у неё для этого больше данных. Если начать слать
   только «рекламные» сделки, алгоритм будет учиться на смещённой выборке
   и деградирует.

2. **Не добавлять браузерное событие Purchase.** Сейчас Purchase уходит только
   с сервера, дублей нет. Это хорошо, так и оставить.

3. **Не отключать автоматический матчинг** и first-party cookie в настройках пикселя.

4. **Не менять `event_name`.** Остаётся `Purchase`.

---

## 5. Отдельная задача: выгрузка для расчёта настоящего k

Коэффициент 3.5 — оценка. Чтобы посчитать фактический, нужна когортная выгрузка.
Это независимая задача, можно делать параллельно с интеграцией.

**Что нужно:**

1. Берём всех клиентов, у кого **первая в жизни покупка** попала в диапазон
   (например, январь–март 2026)
2. Для каждого: сумма **всех его платежей** за **6 месяцев** после первой покупки —
   любой клуб, любой тариф, перерывы включены
3. Разрезы: тип первого тарифа (`monthly` / `annual` / `daily`)

**Формат:**

| client_id | first_purchase_date | first_tariff_family | first_club_id | first_payment | revenue_6m |
|---|---|---|---|---|---|

`k` считается как `sum(revenue_6m) / sum(first_payment)` внутри каждой группы
по `first_tariff_family`.

**Важно:** ничего не нужно решать про «что считать оттоком» или как учитывать
переходы между клубами и тарифами. Считаем просто все деньги от этого человека
за 6 месяцев. Ушёл, вернулся, перешёл на годовой со скидкой, сменил клуб —
всё это просто его платежи внутри окна.

Если в выгрузке будет ещё и `first_club_id` — сможем позже проверить,
отличается ли удержание по клубам. Сейчас исходим из того, что не отличается.

## 6. Проверка

**До выкатки в прод:**
- Meta Events Manager → Test Events: отправить тестовые сделки всех трёх типов
  тарифов, убедиться что `value`, `currency`, `tariff_family` приходят
- Проверить, что `event_id` уникален и не повторяется

**После выкатки:**
- Events Manager → Event Match Quality по Purchase: не должно упасть
- Объём событий Purchase: не должен измениться (мы меняем value, не количество)
- Средний `value` по Purchase должен вырасти примерно втрое —
  это ожидаемый и правильный результат

---

## 7. ⚠️ Что будет сразу после выкатки — предупредить команду

**1. Группы с оптимизацией VALUE уйдут в обучение заново.**
Четыре группы сейчас торгуются по value. Смена шкалы — это для алгоритма
новый сигнал, он перестраивается 7–14 дней. В этот период их результаты
будут скакать. **Не судить о них и не выключать раньше двух недель.**

**2. ROAS в отчётах вырастет примерно втрое.**
Не потому что реклама стала лучше, а потому что value стал ближе к правде.
Все, кто смотрит дашборды, должны знать дату переключения — иначе решат,
что что-то сломалось или что кто-то накрутил цифры.

**3. Целевые CPA и ROAS придётся пересчитать** — старые пороги
перестанут что-либо значить.

**Рекомендация по срокам:** выкатывать в начале месяца, не в середине
рекламной кампании, и зафиксировать дату — она понадобится для всех
последующих сравнений периодов.

## 8. Резюме объёма работ

| Задача | Оценка | Приоритет |
|---|---|---|
| `action_source` по каналу сделки (сайт / клуб / приложение) | 2–4 ч | 🔴 высший |
| Формула value + конфиг коэффициентов | 2–4 ч | 🔴 высший |
| Сохранение `fbclid` / `_fbp` при заходе на сайт (если ещё нет) | 1–2 ч | 🟡 |
| Поля `tariff_family`, `club_id`, `first_payment`, `ltv_multiplier`, `order_id` | 1–2 ч | 🟡 |
| Обработка промо «перша неділя за 1 ₴» | 1 ч | 🟡 |
| Тестирование в Test Events | 1–2 ч | — |
| **Итого разработка** | **~1–1.5 дня** | |
| Когортная выгрузка (раздел 5) | отдельно, 2–4 ч аналитика | 🟢 параллельно |

Если объём надо резать — резать снизу. `action_source` и формула value
дают почти весь эффект; остальное улучшает точность и удобство анализа.
