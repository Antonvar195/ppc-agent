# ARCHITECTURE.md — система управления рекламой Apollo Next

Документ описывает целевую систему, которая заменяет PPC-специалиста:
не набор тулов, а **контур управления планом**.

Дата: 2026-07-29. Обновлять при изменении архитектурных решений.

---

## 1. Что заменяем

Работа PPC-специалиста раскладывается на четыре вещи:

| Что делает специалист | Кто делает в системе |
|---|---|
| Раз в месяц превращает план продаж в структуру кампаний и бюджетов | Консультант + ты (месячный контур) |
| Каждый день смотрит, не сломалось ли, и не выгорели ли креативы | Аналитик (дневной контур), автоматически |
| Раз в неделю двигает бюджеты и хоронит проигравшие креативы | Аналитик → консультант → твой апрув |
| Помнит, что уже пробовали и чем кончилось | Журнал решений |

Ключевое: **система — это сервопривод к плану**, а не генератор отчётов.
Все решения принимаются от разрыва между прогнозом и планом, а не от вчерашней цифры.

## 3. Фундамент измерения

### 3.1 Как устроен учёт

Purchase-события приходят в Meta **через CAPI из CRM** — это реальные сделки, а не
браузерные догадки пикселя. Проверено аудитом (раздел 9): server-side события ≈ количеству
Purchase, браузерных дублей нет.

Значит расхождение Meta и CRM — **не выдуманные конверсии, а разное присвоение кредита**:

- Meta забирает сделку, если человек кликнул за 7 дней или **посмотрел за 1 день**
- CRM отдаёт сделку последней UTM-метке
- CRM хранит только последнее касание (до заполнения формы пользователь анонимен),
  поэтому **свою модель атрибуции построить нельзя**

### 3.2 Интервал правды

Отсюда главное правило системы: **у нас нет точки, у нас интервал.**

```
CRM last-touch  ──────────── правда ──────────── Meta 7d click + 1d view
(пессимистичная граница)                          (оптимистичная граница)
```

Замеренная ширина интервала (данные аудита, 30 дней):
Meta claims **504** покупки, всего на сайте **~1 685**. Meta приписывает себе **~30%** продаж.
CRM last-touch по оценке даёт Meta **~15%**. Интервал: **15–30%**.

**Причина ширины найдена:** 62% конверсий, которые Meta себе приписывает — **view-through**
(человек увидел, не кликнул). CRM их не видит по определению.

Как с этим жить:
- **Планировать** в CRM-единицах (пессимистично) — не окажешься в минусе
- **Оптимизировать внутри Meta** в Meta-единицах — они самосогласованы
- **Никогда не смешивать** в одной метрике
- Найти точку внутри интервала можно **только гео-холдаутом** (раздел 8)

### 3.3 Окно атрибуции короче цикла сделки

Данные аудита по окнам (30 дней):

| Окно | Покупок |
|---|---|
| 1d_view | 340 |
| 1d_click | 140 |
| 7d_click | 205 |
| 28d_click | 280 |

**28d_click / 7d_click = 1.37.** То есть **37% click-продаж приходят позже 7-го дня.**
Цикл принятия решения о покупке абонемента длиннее окна атрибуции.

Следствия, обязательные к учёту:
1. Судить креатив на 7-й день — недосчитать его больше чем на треть
2. Креативы с длинным циклом (дорогой оффер, годовой абонемент) системно проигрывают
   импульсным при коротком окне — это артефакт измерения, а не качества
3. **Отчётность вести по 28d_click** (окно доступно, проверено), оптимизацию оставить
   на 7d_click+1d_view — Meta оптимизирует только по нему
4. Вердикт по креативу выносить не раньше **10-го дня** жизни

## 4. План как контракт

Центральный объект системы. Всё остальное — приводы к нему.

План задан **по клубам** (общее количество продаж в месяц), внутри клуба разбит по
источникам. Meta — один из источников, её доля сильно зависит от стадии клуба.

```yaml
# plan/2026-08.yaml
month: 2026-08
currency: USD

clubs:
  - id: "019"
    name: DREAM
    city: Kyiv
    mode: mature                    # mature | presale
    goal_sales_total: 180           # общий план клуба, все источники
    source_mix:
      meta: 0.12
      google: 0.30
      organic: 0.35
      offline: 0.23
    goal_sales_meta: 22             # 180 × 0.12 — вычисляется
    budget_meta: 260
    guards:
      freq_max: 3.0
      reach_target: 45000

  - id: "041"
    name: Вінниця-2
    city: Vinnytsia
    mode: presale
    open_date: 2026-09-15           # дедлайн важнее конца месяца
    goal_sales_total: 400
    source_mix: { meta: 0.90 }
    goal_sales_meta: 360
    budget_meta: 3200
    target_cpa: 8.90                # budget / goal — вычисляется
    max_cpa: 13.00

concepts_pool: [C1, C3, C7, C9]     # что дал дизайнер на месяц
test_budget_share: 0.15             # доля бюджета на новые концепты
```

Кампании **выводятся** из плана клубов, а не наоборот. Pacing считается на уровне клуба —
там, где реально стоит цель.

### 4.1 Правило перераспределения бюджета

- **Внутри клуба** (между группами, аудиториями, креативами) — свободно, по эффективности
- **Между клубами** — только если клуб физически не может освоить бюджет, или ты
  сознательно меняешь план

Иначе система сольёт весь бюджет в самый дешёвый город и оставит пустыми клубы,
которые надо грузить. Meta-CPA зрелого клуба выглядит плохо **по построению** —
это не повод забирать у него деньги.

## 5. Два режима работы

Надёжность Meta-атрибуции — функция доли Meta в миксе. Отсюда два разных playbook'а.

| | PRESALE (новый клуб) | MATURE (зрелый клуб) |
|---|---|---|
| Доля Meta | до 90% | до 15% |
| Интервал правды | узкий, границы сходятся | широкий (15–30%) |
| Главная метрика | CPA по Meta-атрибуции | стоимость охвата в радиусе клуба + частота |
| Дедлайн | дата открытия | конец месяца |
| Бюджет | переменная, управляется по CPA | фиксированная доля плана клуба |
| Ротация креативов | агрессивная, узкое гео выгорает быстро | по частоте и CTR-decay |
| Проверка правды | CRM через неделю — сходится | CRM помесячно + гео-холдаут |
| Автономия системы | давать здесь первой | почти никогда |

## 6. Банк креативов: концепт ≠ исполнение

Развязка, ради которой система имеет смысл.

- **Концепт** — идея, хук, оффер. Даёт дизайнер, пачкой на месяц.
- **Исполнение** — конкретный рендер. Делает `creative_variants` за минуты.

```
Концепт C3 — «-50% на годовой, дедлайн»
  ├── C3-e1  видео вертикаль   active    день 12, CTR 1.8%, freq 2.1
  ├── C3-e2  баннер квадрат    fatigued  CTR −40% от пика, freq 4.3
  └── C3-e4  аналог C3-e1      queued
```

### 6.1 Два разных правила — их постоянно путают

**Выгорание меряется на исполнении:**
```
CTR упал ≥ 30% от собственного пика (скользящее 3-дневное)
  И частота ≥ 3.0 (mature) / ≥ 4.0 (presale, узкое гео)
  И потрачено ≥ 3 × target_cpa (иначе это шум)
```

**Решение принимается на концепте:**
- Концепт в плюсе (CPA всех исполнений ≤ target) → генерим аналоги **лучшего исполнения**,
  концепт живёт месяцами
- Концепт слабый → хороним целиком, достаём следующий из пула дизайнера

### 6.2 Как расходуется месячная пачка

Пачка от дизайнера — это **месяц гипотез, а не месяц откруток**.
2–3 новых концепта в неделю на `test_budget_share` бюджета, параллельно с масштабированием
уже победивших. Победители масштабируются аналогами, а не новыми концептами.

### 6.3 Состояния

```
backlog → testing → active → fatigued → retired
                       ↑         │
                       └─ аналог ┘
```

## 7. Три контура управления

### Дневной — операционка (автоматом, без тебя)

Смотрит **только на то, что уже устоялось за сутки**:
темп спенда, CPM, CTR, частота, cost per landing_page_view, детект выгорания.

**Не трогает конверсии и CPA** — они ещё дописываются окном атрибуции.

Главная петля:
```
ночь    ETL → диагностика → флаг «C3-e2 выгорел»
        ↓
        концепт C3 в плюсе? — да, CPA $11.2 при target $12.5
        ↓
        creative_variants: 2 аналога с C3-e1 (лучшее исполнение концепта)
        ↓
утро    Telegram: превью + цифры + [заменить / нет / другой концепт]
        ↓
апрув   publisher: новые объявления в ту же группу, старое → PAUSED
        ↓
        журнал решений: гипотеза «аналог держит CPA концепта»
        ↓
+3 дня  post-check → факт в журнал
```

Это единственное место, где позже стоит дать автономию: действие обратимо,
ограничено одной группой, качество измеримо по журналу.

### Недельный — тактика

Сигнал: **заявки из CRM по UTM**. Их на порядок больше, чем продаж
(за 28 дней: Lead 4 039 + Contact 4 741 против Purchase 1 573), значит
статзначимость набирается в разы быстрее. Плюс Meta-конверсии по данным старше 10 дней.

Что делает:
- разрыв с планом по каждому клубу + прогноз на конец месяца
- декомпозиция изменения CPA: ΔCPA = f(ΔCPM, ΔCTR, ΔCR) — настоящий ответ на «почему подорожало»
- вердикты по тестам концептов с проверкой значимости
- **конверсия заявка → продажа в разрезе креатива** — детектор «дешёвый креатив
  приводит плохих людей». Много дешёвых заявок при низкой конверсии = креатив врёт в оффере
- перераспределение бюджета внутри клубов

### Месячный — стратегия

- сверка с CRM, калибровка коэффициента `k` по клубам
- ревизия source_mix: подтвердилась ли доля Meta
- новый план, распределение концептов, бэклог тестов
- ревизия LTV в `business.yaml`

### Горизонты метрик — сводка

| Контур | На что смотрит | Чего **не** трогает |
|---|---|---|
| День | темп, CPM, CTR, частота, выгорание | конверсии, CPA |
| Неделя | заявки CRM, Meta-конверсии старше 10 дней | продажи (дозакрываются) |
| Месяц | продажи CRM, заявка→продажа, калибровка, LTV | — |

## 8. Слой сверки

### 8.1 Коэффициент калибровки

Раз в месяц по каждому клубу и типу кампании:
```
k = продажи_из_CRM_с_меткой_meta / продажи_по_Meta-атрибуции
```

Не для того, чтобы «исправить» Meta — для перевода между системами координат
и для контроля дрейфа. Ожидаемо: presale `k ≈ 0.8–1.0`, mature `k ≈ 0.2–0.4`.
Резкий уход `k` = сломалась разметка или изменилось поведение канала → алерт.

### 8.2 Гео-холдаут

Единственный честный способ узнать, где внутри интервала 15–30% правда.
Раз в квартал: гасим Meta в одном зрелом клубе на 3 недели, сравниваем его общие
продажи с сопоставимыми клубами. Специалист такое не делает — руки не доходят.
Система ставит в расписание и считает.

### 8.3 Джойн CRM ↔ Meta

UTM-шаблон уже даёт уровень объявления:
```
utm_source=facebook&utm_medium={тип}&utm_campaign={{campaign.name}}
&utm_content={{ad.name}}&utm_term={{adset.name}}&placement={{placement}}
```

Ключ джойна: `(utm_campaign, utm_term, utm_content)` — уникален.

**Объявления не переименовывать после старта.** UTM зашивается в момент клика.
Переименовал — вся история продаж по нему повисает. (Соблюдается.)

### 8.4 Идентификатор концепта

**Что концепт описывает по сути: аргумент, почему человек должен купить.**
Больше ничего.

Что в концепт **не** входит и почему:

| Не входит | Почему |
|---|---|
| Формат (видео / баннер / вертикаль) | свойство исполнения, меняется внутри концепта |
| Гео, клуб, город | свойство кампании — один аргумент крутится в разных городах |
| Визуал, модель, локация съёмки | свойство исполнения |
| Тариф | может меняться в рамках того же аргумента |

Если зашить в концепт гео или формат — данные фрагментируются: одна и та же идея
в Киеве и Львове становится двумя концептами, и статистики не хватит именно там,
где она нужна — на вердикте по концепту.

### Схема: буква семейства + номер

```
P03  →  P = семейство (ценовой аргумент), 03 = порядковый номер
```

| Буква | Семейство | Аргумент |
|---|---|---|
| **P** | Price | цена, скидка, рассрочка, перша неділя за 1 ₴ |
| **D** | Deadline | дедлайн акции, «до 31.07», обратный отсчёт |
| **N** | New | открытие клуба, пресейл, новый зал |
| **L** | Location | клуб рядом, в ТРЦ, по дороге с работы |
| **R** | Result | форма, похудение, трансформация |
| **S** | Social | комьюнити, тренеры, атмосфера, отзывы |
| **F** | Feature | оборудование, групповые, зоны, часы работы |

Семейство — не украшение, это **аналитическое измерение**, ради которого всё
и затевается. Оно даёт вердикты уровнем выше отдельного концепта:
«ценовые дают CPA $9 при конверсии заявка→продажа 22%, локационные — CPA $14
при конверсии 41%». Такой вывод меняет медиаплан; вывод про отдельный креатив — нет.

**Правило снятия неоднозначности.** Креатив «-50% тільки до 31 липня» — и цена,
и дедлайн. Семейство определяется по **аргументу в хуке**: что стоит в заголовке
или в первые 2 секунды. Второй аргумент пишется в `tags` реестра, не в ID.
Один концепт — одно семейство.

**Где граница между новым исполнением и новым концептом:**
изменился аргумент → новый концепт. Изменилось только то, **как** аргумент показан
(другая модель, другой монтаж, другой фон) → новое исполнение того же концепта.
Одинаковое обещание в заголовке = один концепт.

**ID никогда не переиспользуется и не переименовывается.**
Номер сквозной внутри семейства, не сбрасывается по месяцам.

### Исполнения

`P03e1`, `P03e2`, … — сквозная нумерация внутри концепта, номера не переиспользуются.
Аналог, сгенерированный из `P03e1`, получает следующий свободный номер и
записывает `derived_from: P03e1`. Это и есть данные, на которых система потом учится,
какие аналоги держат качество, а какие только CTR.

### Имя объявления

```
баннер:  {DDMM}_{N}_{концепт}{исполнение}      →  1506_2_P03e4
видео:   {DDMM}_video{N}_{концепт}{исполнение} →  1506_video2_P03e4
```

Из одной строки CRM-выгрузки читается всё: запущено 15.06, второй креатив в запуске,
ценовой концепт №3, исполнение №4. Реестр для джойна не нужен — имя самодостаточно.

Парсер суффикса: `/_([PDNLRSF])(\d{2})e(\d+)$/`

### Реестр `creatives/bank.yaml`

```yaml
concepts:
  - id: P03
    family: price
    name: "Річний за половину ціни"
    hook: "Річний абонемент −50%"
    tags: [deadline]              # вторичные аргументы
    source: designer              # designer | generated
    created: 2026-07-15
    status: active                # backlog | testing | active | retired
    executions:
      - id: P03e1
        format: video_vertical
        file: creatives/out/1506_video2.mp4
        state: active
        launched: 2026-07-15
      - id: P03e4
        format: video_vertical
        derived_from: P03e1
        state: queued
```

**Старые объявления без суффикса** не трогаем — переименование рвёт UTM.
Их можно задним числом сопоставить с концептами прямо в реестре, полем `legacy_ads`,
если понадобится история глубже месяца.

## 9. Аудит CAPI — результаты 2026-07-29

Запуск: `node tools/audit_capi.js` (read-only).

### Что настроено хорошо

| Проверка | Результат |
|---|---|
| Датасет | Apollo `393751978682816`, стреляет, последнее событие свежее |
| Источник Purchase | **только server-side** (SERVER 408 ≈ Purchase 414 за 7 дней) |
| Дубли браузер/сервер | **нет** — браузер Purchase не шлёт |
| Автоматический матчинг | вкл: `em, ph, fn, ln, db` |
| First-party cookie | включён |
| Циркулярность | **нет** — в CAPI уходят все сделки (1 573 за 28 дней), а не только те, что CRM приписала Meta |

Это сильная конфигурация. Основные способы сломать CAPI здесь не сработали.

### Что требует действий

**🔴 1. В value уходит первый платёж, а не LTV**

```
Расход за 30 дней:   $29 995.95
Покупок (Meta):      504
Сумма value:         $16 564.32
Средний чек:         $32.87        ← первый платёж
ROAS:                0.55          ← выглядит как убыточный аккаунт
```

В `google_audit-rules.md` зафиксировано: LTV ≈ 3–4 месяца подписки.
Значит реальная ценность ≈ $98–131, реальный ROAS ≈ **1.6–2.2**.

Проблема не в отчёте, а в **оптимизации**: алгоритм охотится за дешёвым первым платежом,
а не за ценным клиентом. Это единственное место, где LTV-логику можно вшить не в аналитику,
а в сам аукцион.

Что делать:
- отправлять `value` = ожидаемый LTV (грубо: тип абонемента × коэффициент по клубу)
- либо добавить второе событие на продление / 2-й месяц как сигнал качества
- пересчитать все целевые CPA после смены — они сдвинутся

**🟡 2. Окно атрибуции короче цикла сделки** — см. 3.3. Перевести отчётность на 28d_click.

**🟡 3. Диагностика Meta:** `pixel_has_low_event_source_match_rate` → failed.

## 10. Витрина фактов

SQLite (`better-sqlite3`), ночной ETL.

```
fact_daily(date, campaign_id, adset_id, ad_id,
           spend, impressions, reach, clicks, frequency,
           purchases_7d_click, purchases_1d_view, purchases_28d_click,
           value, leads, landing_views, PRIMARY KEY(date, ad_id))

dim_ad(ad_id, ad_name, adset_id, concept_id, execution_id,
       format, creative_hash, launched_at, state)
dim_adset(adset_id, adset_name, campaign_id, geo, audience, placements)
dim_campaign(campaign_id, campaign_name, type, geo, club_ids, month)

fact_crm_daily(date, club_id, utm_campaign, utm_term, utm_content,
               leads, sales, revenue)

decisions(id, ts, type, object_id, hypothesis, expectation,
          fact_json, verdict, filled_at)
```

**Критично: ETL перезабирает хвост в 10 дней, а не только вчера.**
Окно атрибуции дописывает конверсии задним числом — при инкрементальной загрузке
история навсегда останется недосчитанной, и все выводы по креативам будут занижены.

Измерения парсятся из нейминга — он у нас жёсткий, это подарок:
`AI_Apollo_reach_Kyiv_summer_1506` → тип, гео, дата;
`Kyiv_18-35_inst` → гео, аудитория, плейсмент;
`1506_video2_C3` → дата, номер, концепт.

```
tools/
  audit_capi.js       ✅ аудит CAPI/пикселя

  db.js               ❌ схема + миграции

analyst/
  pacing.js           ❌ факт vs план, прогноз на конец месяца/до открытия
  decompose.js        ❌ ΔCPA = f(ΔCPM, ΔCTR, ΔCR)
  diagnostics.js      ❌ детерминированный rule engine → флаги с severity
  fatigue.js          ❌ детект выгорания на уровне исполнения
  experiments.js      ❌ вердикты по тестам со значимостью
  creative_report.js  ❌ сквозной рейтинг концептов и исполнений
  crm_sync.js         ❌ выгрузка CRM по UTM + калибровка k

advisor/
  preflight.js        ❌ проверка нового запуска против истории (до publisher)
  budget.js           ❌ перераспределение внутри клуба
  backlog.js          ❌ очередь тестов = матрица минус пройденное
  mediaplan.js        ❌ месячный план из целей по клубам
  narrate.js          ❌ LLM-слой: объясняет и приоритизирует ГОТОВЫЕ числа

context/
  business.yaml       ❌ юнит-экономика, LTV, целевой CAC
  clubs.yaml          ❌ клубы, стадии, ёмкость, приоритеты
plan/
  YYYY-MM.yaml        ❌ план-контракт
creatives/
  bank.yaml           ❌ концепты, исполнения, состояния
```

**Правило, которое нельзя нарушать:** числа считает код, LLM только объясняет
и приоритизирует. LLM не должен видеть сырой API-ответ и выводить из него цифру —
только готовый структурированный результат. Иначе получишь красивый текст
с выдуманными числами.

## 13. Порядок сборки

1. **Смена value на LTV в CAPI** — не код системы, но перевешивает половину остального.
   Делать первым.
